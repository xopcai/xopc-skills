# Threat model output contract

## Scope and assumptions

- In-scope repository paths and explicitly excluded components
- Intended deployment and exposure
- Evidence sources
- Material assumptions and unanswered questions

## System model

| Component | Role | Data/assets | Evidence |
|---|---|---|---|

List trust boundaries and entry points separately. Each boundary should name both sides, protocol, and evidenced controls.

## Prioritized abuse paths

| ID | Abuse path | Preconditions | Assets/impact | Existing controls | Likelihood | Impact | Priority | Evidence/confidence |
|---|---|---|---|---|---|---|---|---|

Keep the list small enough to review. Preserve uncertainty instead of manufacturing precision.

## Mitigations and validation

Map every recommendation to threat IDs, a concrete control location, an owner when known, and an observable validation. Separate immediate risk reduction from longer-term design work.

## Residual risk

State uncovered entry points, unverified controls, deployment facts that could change ranking, and any specialist review still needed.
