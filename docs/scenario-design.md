# Scenario-first Design

## 场景不是分类标签

一个有效场景必须能写成：

> 当 `[用户角色]` 面临 `[触发情境]`，希望从 `[输入/现状]` 得到 `[可交付结果]`，并满足 `[关键约束]`。

“编程”“生产力”“搜索”只是分类；“把一个使用 OpenAI SDK 的 Node 服务迁移到 XOPC，并通过流式回归测试”才是可评测场景。

## 场景立项所需证据

- 至少三个真实或高度可信的用户表达，不应全由作者改写成同一种句式。
- 当前完成方式、耗时、失败点和已有替代方案。
- 预期输出和用户判断成功的方式。
- 不适用边界、危险操作和权限需求。
- 为什么通用 Agent、单一 Connector 或普通文档不足以完成任务。

## 场景评分

每项 0–3 分，总分只用于排序，不能绕过硬门禁：

| 维度 | 说明 |
|---|---|
| Frequency | 任务是否重复发生 |
| Pain | 当前成本或失败影响 |
| Skill lift | Skill 相比通用 Agent 的潜在提升 |
| Verifiability | 是否能验证结果 |
| XOPC advantage | XOPC 是否有独特知识或基础设施 |
| Maintainability | 能否长期维护依赖和内容 |

建议总分达到 12/18 后进入原型阶段；涉及高风险或许可证不清的场景仍然停止。

## 从场景到 Skill 边界

一个 Skill 应覆盖一个完整且可组合的工作单元。过窄会让一次任务加载多个相互冲突的 Skill；过宽会导致错误触发和无关上下文。

确定边界时明确：

- Trigger：何时应该使用。
- Near misses：哪些相近请求不应该使用。
- Inputs：最低必要输入和可自动发现的信息。
- Outcome：用户最终拿到什么。
- Non-goals：明确排除哪些工作。
- Recovery：缺信息、工具失败或验证失败时如何继续。
